# 0.3 errata

Deviations from the 0.3 plans (plans/0.3) found while building, numbered E3-n. Chapters and decisions win over plans; this file records where a plan was wrong, incomplete or changed.

- E3-1: P1-T1. `ACTIVE_MILESTONE` is M03 and `tests/codes.rs` lists the 42 M03 codes no test asserts yet as `PENDING_0_3` (the master plan's list also names `HN-D006`, which has been M02 since 0.2). M03 is the last milestone of the code table, so no registered code is inactive any more: the tests that inactive codes are dropped (`r_arch_055__load_diagnostics_pass_through_floor_stays_enforce_and_inactive_codes_vanish`, `r_agt_009__a_floor_finding_cannot_be_lowered_and_inactive_codes_are_dropped`) now use an unregistered code, `XX-Z999`, and `r_arch_055__later_milestone_codes_are_registered_but_inactive` asserts the M03 codes are active. The crate version stays 0.2.2 and the pin stays 0.2.0 until the 0.3 release, as in 0.2 (E2-75): raising either now re-blesses every golden and refuses the in-tree binary. The 0.2 golden outputs are the regression fixture as they stand (P7-T6). A draft change doc covers P1's product changes, widened as P1 lands.
- E3-2: D-64 moved the v1 API freeze to the end of 0.4; P7-T7 writes and snapshots the 0.3 surface without freezing it, and P7-T9 (names reserved for 0.4) is withdrawn.
- E3-3: P1-T2. The root control file parses `[layers.<ladder>]` (layer = rank), `[free.<name>]` (`of`, `may-use`, `usable-by`; a `rank` key is an error, R-HIER-005), `[[flow]]` (`from`, `to` as a string or list, `via`), `[layer-policy."<ladder>.<layer>"] used-by = "entry"`, `[hier]` (`level` 0 to 3, `same-rank`, `unbound-ok`, `governed`, `promote` with `fan-in-containers` 3 and `single-consumer-seals` 4 by default) and `[kinds.K] layers` into `ControlFile::hier` (`config/hier.rs`). Every layer reference (free-layer lists, flows, policies, kind layers) must name a declared layer or `<ladder>.*` of a declared ladder, else the file fails (`HN-C001`). A free layer is named by its own name or as `<of>.<name>`. No `[hier]` table means hierarchy is off (`level` is `None`); `[hier]` without `level` is level 0. The five tables are root-only (R-HIER-001): in a child file they are stripped as `HN-C003` with the escalation hint, which is R-HIER-004's "an attempt to reorder becomes an escalation proposal". R-HIER-004's child aliasing and `accepts=` are not built: no chapter defines their syntax (the schema index has no such key); they wait for a definition. `fairlead new ladder ui|core` scaffolds the two presets of 30-hierarchy into the root control file (D-20): the UI ladder with `[free.chrome]`, the core ladder with `core.shell` as entry-only; a ladder already declared refuses, another name is a usage error, and so is a non-root scope. `new request` stays reserved until P3. The unit-side half of R-HIER-003 (a `def`'s `layer=` names a declared layer) lands with the units in P1-T3/T4.
- E3-4: P1-T3. Declarations in code (D-40). In 0.1 and 0.2 a code `def` only marked an implementation site of an item declared in a doc, so a code-shaped kind could not be declared at all (`new` refused it and told the user to write a code `def`, which `check` then reported as `HN-R001`). From 0.3 a code `def` declares its item when its kind is `shape = "code"`, its kind lists `layers` (a unit kind), or the `def` carries `layer`, `container`, `parent` or `path`; a doc declaration of the same ID in the scope or any ancestor wins (the `fullstack-tauri` golden declares a code-shaped `cmd` kind in a root doc and implements it in a child scope; without the chain rule that became `HN-R005`), and of several code `def`s the first by path and line declares (the others stay sites). No 0.2 golden output changed. Test `r_hier_013__a_doc_declaration_up_the_chain_wins_over_a_code_def`. The 0.3 `def` keys of 30-hierarchy (`layer container parent path see steps on-error etype unit reaches implements spell exposure role proto dir wire ver params ts rs contract side`) and the `use` keys `dyn` and `pin` are known keys of edition 1 (master Q-1's default: new keys on known verbs, no edition 2). The chapter never says how a kind becomes a container kind (its preset only comments `[kinds.ctr]  # container`), so the model infers it (`hier::Model`): a unit is an item whose kind lists `layers` or that has `layer=`; a container is a non-unit item named by a unit's `container=` or a container's `parent=`, or one that declares `parent=` or `path=`. Checks (`HierCheck`, on only when `[hier]` exists): level 0, `HN-H001` for container claims that overlap without one container nested in the other (literal glob prefixes, scope-relative) and for a claim that leaves its scope (`..`), and `HN-H002` for a parent cycle, on each container of the cycle; level 1, `HN-H001` for a unit with two or more `container=` values (R-HIER-012: a second membership is `see=`), `HN-H023` for a unit with `path=` and a code `def` site, and the unit half of R-HIER-003 as `HN-H007` (no layer where the kind requires one, a rank number, an undeclared layer, a layer the kind's `layers` do not allow); the code table has no separate code for a bad layer, and `hier.rank` is the rule a wrong layer breaks.
