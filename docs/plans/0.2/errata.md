# 0.2 errata

Deviations from the 0.2 plans, in the order they were made. The chapters and decisions.md win over the plans; the plans are not edited by executors.

- E2-1: P1-T1. `ACTIVE_MILESTONE = M02` and `PENDING_0_2` (40 codes, with a second test that fails when a listed code becomes asserted, so the list only shrinks). The workspace version stays `0.1.0` until the 0.2 release: the `check` header carries the binary version, so a `-dev` bump mid-milestone would churn every golden. Edition-1 byte stability is `tests/editions.rs` (`r_edn_051__...`): every golden that `sync` accepts must regenerate its committed `gen/` files byte for byte (CRLF checkouts compared after line-ending normalisation, R-GIT-013), instead of a copied `tests/editions/1/` tree. Two 0.1 tests that used `HN-V001` as their "inactive code" example now use `HN-H001` (0.3).
- E2-2 (owner, 2026-10-10): agent-run protocols use `opencode-go/muse-spark-1.3-contributor` (agent-runbook, shared rule 4).
- E2-3: P1-T2, P1-T3. `version.rs`: `Version` (strict `MAJOR.MINOR.PATCH`), `Impact`, `bump`, `VersionLine`, `derive_line`, `mirror_divergence`. With no pending doc, `O` is `S` bumped by `fix`, so `O` is always ahead of `S`; the chapter does not say what `O` is when nothing is pending. Spec gap: R-VER-004 says `check` SHOULD warn on mirror divergence, but chapter 13 has no code for it; the text is computed and waits for an owner-assigned code (proposed `HN-V017 H-VER-MIRROR`, warn).
- E2-4: v0.1.0 released (owner request): tag `v0.1.0`, GitHub release with three binaries and `blake3sums.txt`, and `fairlead-syntax`, `fairlead-core`, `fairlead` 0.1.0 published to crates.io from a clean worktree of the tag.
- E2-5: P1-T4. `docs.rs` (change-doc model: `DraftId`, `Status`, `ChangeDoc`, `parse_change_doc`, `collect_change_docs`, `readiness_problems`, `slug`) and `new change "<title>" [--field impact=..] [--field covers=..]`, planned through `pipeline::plan_new` (it needs the version line; `write::new_plan` refuses `change` directly). Change docs live in `<scope>/<folder>/docs/changes/d-<draft>-<slug>.md`; the chapters fix the filename but not the folder. Change-doc kinds: change, chore, mechanical, bulk, revert, retarget, early-removal, revive, upgrade. The 40 random bits come from the standard library's OS-seeded `RandomState` (no clock, no new crate). Not yet: the `[version]` control table (`start` is fixed at 0.1.0 until it is parsed), the check-side `H-DOC-EMPTY` (HN-V009) for an incomplete `ready` doc, and resolution of `d-<draft>` in doc-reference keys (R-VER-049); they land with the seal planner (P1-T8) and the refs work (P3-T7).
- E2-6: P1-T5. Ordinals (`docs::assign_ordinals`, per scope and kind, ordered by `created` compared as versions, then draft ID), the alias map `gen/alias` (`d-<draft> kind=<k> ord=<nnnn>`, written by `sync` only for scopes that hold a sealed doc, so 0.1 trees are unchanged), and the `versions` built-in: `H-ID-COLLISION` (HN-V006, same draft ID with a different content hash; identical copies are not reported), `H-ORD-DUP` (HN-V007), `H-DOC-EMPTY` (HN-V009, incomplete `ready` doc; also used for a change doc whose frontmatter is unusable, which chapter 13 gives no code of its own). An ordinal's scope is the doc's `scope` key. Deferred: `new --reid` (rename the later doc and rewrite references) lands with `seal --reseal` (P1-T13), which shares the rewrite.
- E2-7: P1-T6. `hist.rs` (module name chosen to avoid `registry::ledger`, the 0.1 exception ledger): year-file parse and render, `record_digest` (8 base32 of blake3 over the normalised record text without ` d=`), `checkpoint_digest` (previous checkpoint digest or header `prev`, then the record digests since), `append_version`, `finalise`, `verify` and `verify_chain`. Record lines after the last checkpoint count as a break: in 0.2 only seal appends, always with a checkpoint. Ledger files are read into `Facts::ledgers`, are no longer scanned for directives (no comment syntax, like fairlead's generated files, E-45), and breaks are `HN-G003` in the `versions` check. `sync` never touches them: the generated set holds no ledger-class path.
- E2-8: P1-T7. `merkle.rs`: `scope_digests` (bottom-up; own files' `path hash` entries from the corpus content hashes, generated files excluded so a lock never hashes itself, then `child <id> <digest>` lines), `ancestor_digest` (only inherited items, `id policy k=v` lines), `scope_lock_body` and `parse_scope_lock`. `gen/scope.lock` is generated only once a version is sealed: a never-sealed tree (every 0.1 tree) gets no new file, so edition-1 output stays byte-identical (R-EDN-002). The lock is not judged by `HN-G001`; `H-SYNC-ANCESTOR` (HN-V004) is info while the lock lags by fewer than 3 seals and warn after (`ancestor-grace`, a constant until `[version]` is parsed); the error at seal belongs to the seal planner (P1-T8). Not done here: `sync` scoped to one scope (R-VER-021): `sync` still writes the whole tree's generated set, which already never rewrites an ancestor's file differently from its own sync; scoping waits for a `--scope` flag on `sync`. The "unchanged files are not read" property is that of the 0.1 cache (E-46), not new code; its 100,000-file benchmark is P7-T5.
- E2-9: P1-T8. `seal.rs`: the pure planner (`plan(&SealInput) -> Result<SealPlan, SealRefusal>`). Preflight order: detached HEAD, unmerged paths, integration branch (`seal-where`), changed files outside the seal's own outputs (`gen/`, `ledger/`, `versions/` under the managerial folder; `--allow-dirty` records `dirty`), `HN-F001` secrets, check errors, incomplete `ready` docs, nothing ready, version already sealed. `O` is bumped from the impacts of the docs being sealed only (drafts are carried and do not bump). A fresh codebase's first seal is `version.start` (`bump = "start"`). The sweep report lists drafts whose `covers` globs match no path and drafts carried through more than `sweep-after` seals (counted as sealed versions at or after `created`). Stubs, as planned: coverage (P2-T3) and the due gate (P3-T6). Deferred: unresolved escalations at seal (R-VER-058, `H-ESC-STALE` HN-V016) need the `[[req]]` age in seals, which arrives with the version-aware ledger in P1-T10.
- E2-10: P1-T9 with the CLI part of P1-T16. The transaction gains `WriteKind::Delete` (journal `new_hash = "-"`, applied once the file is gone, restored from its backup on rollback) and `WriteSet::commit_point`, applied after every other write (`apply_order`). `WriteSetKind::Seal` may write only `gen/**` (generated), `ledger/hist/<year>.hl` (ledger), `docs/**.md` and the root's `versions/<v>.md` (authored). `seal::write_set` builds the R-VER-059 write-set: each sealed doc is rewritten (`toml_edit`: `status`, `sealed`, `body-hash = "b3:<20 base32>"` of the body after the frontmatter, `ordinal`) at `<ordinal:04>-<slug>.md` and its draft-named file deleted; one ledger record per sealed doc (`<draft> kind ord impact title`) plus a checkpoint in `<scope>/<folder>/ledger/hist/<year>.hl`, finalising the previous year with `# end` when the year changes; every resolved scope's `scope.lock` and alias map; the version file last. `sealed-at` is the `--as-of` date at 00:00 UTC: retention needs days, and the seal adds no clock read to the dogfood waiver. `--resume` is the 0.1 recovery (every writer rolls an interrupted journal forward first); `--abort` and `--reseal` arrive with P1-T13. `fairlead seal [--dry-run] [--yes] [--allow-dirty] [--anywhere]` replaces the reserved verb; the integration branch is `main` and `--anywhere` stands for `seal-where = "any"` until `[version]` is parsed. Tests: `tests/seal.rs` (plan only, exact write-set and a clean check after, idempotent rerun, integration branch, dirty tree).
- E2-11: P1-T11. `H-SEAL-TAMPER` (HN-V003): the `versions` check compares each sealed change doc's recorded `body-hash` with `docs::body_hash` of the file now, which `collect_facts` computes for every Markdown file under a `docs/changes/` folder (`Facts::doc_body_hashes`). Not done: the `mutable = true` doc class with changelog-recorded typo fixes (R-VER-054); change-doc kinds are fixed and none is mutable, so it waits for doc-kind mutability in the kind schema. Version files carry no hash, so their immutability rests on review and on the ledger checkpoints that record each sealed version.
- E2-12: P1-T12. `seal --commit [--tag]` (clap: `--tag` requires `--commit`). `GitRepo::commit_paths` runs `git add -A -- <written paths>` then `git commit -q -m "seal <v>" -m "Fairlead-Version: <v>" --only -- <paths>`, so exactly the seal's files are committed even if the user staged others; `GitRepo::tag` runs `git tag -a fairlead/<v>`. Both use the user's `git` executable in the foreground from `git.rs`, whose guard test now also forbids process spawning anywhere else in `fairlead-core` (R-GIT-076). A missing `git` is a usage error naming the flags.
- E2-13: P1-T13 (checks). `H-VER-COLLISION` (HN-V001): a version file with merge-conflict markers (an add/add conflict of two seals of one version) or whose `version` key differs from its file name. `H-VER-GAP` (HN-V002): sorted version files must chain through `prev` (the lowest has none), so a seal commit cherry-picked alone, or a missing predecessor, is reported. Reverting a seal commit needs no code: `S` is derived, so the line simply ends one lower (R-GIT-034). `backport-of` needs no exception either: identical copies are never `H-ID-COLLISION`. Version texts come from `Facts::version_texts` (the root's `<folder>/versions/*.md`, read raw because conflict markers break frontmatter parsing). Deferred: `seal --reseal` and `new --reid` (renumber an unintegrated seal; give a colliding draft a new ID and rewrite references). Both rewrite sealed history, and they are planned next to `move`'s rewrite engine (P5), which does the same reference rewriting.
- E2-14: `H-TX-INCOMPLETE` (HN-V005, R-VER-051, R-GIT-051) in the `versions` check: a ledger checkpoint whose version has no version file (a seal stopped before its commit point), or a leftover `.fairlead/sync.journal` (`Facts::pending_journal`). Recovery stays the 0.1 rule: any writer resumes or rolls back the journal first.
- E2-15: P1-T10 (part). Rollups at seal: every touched scope and each of its ancestors gets one ledger record `rollup.<v> kind=rollup waivers=<own effective> subtree-waivers=<sum over the subtree> digest=<Merkle digest>`, so the root's ledger answers for its subtree without descending (R-VER-052). The version-file body lists one line per sealed doc (`- <impact>: <title> (<scope>, <draft> <ordinal>)`). Deferred to the phases that produce the data: deprecated-reference burn-down (P3-T7), exceptions added and expired per version, items due next and graveyard additions in the body (P3), and the optional `changelog.file` aggregate (with the `[version]`/`[changelog]` tables).
