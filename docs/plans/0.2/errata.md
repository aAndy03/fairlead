# 0.2 errata

Deviations from the 0.2 plans, in the order they were made. The chapters and decisions.md win over the plans; the plans are not edited by executors.

- E2-1: P1-T1. `ACTIVE_MILESTONE = M02` and `PENDING_0_2` (40 codes, with a second test that fails when a listed code becomes asserted, so the list only shrinks). The workspace version stays `0.1.0` until the 0.2 release: the `check` header carries the binary version, so a `-dev` bump mid-milestone would churn every golden. Edition-1 byte stability is `tests/editions.rs` (`r_edn_051__...`): every golden that `sync` accepts must regenerate its committed `gen/` files byte for byte (CRLF checkouts compared after line-ending normalisation, R-GIT-013), instead of a copied `tests/editions/1/` tree. Two 0.1 tests that used `HN-V001` as their "inactive code" example now use `HN-H001` (0.3).
- E2-2 (owner, 2026-10-10): agent-run protocols use `opencode-go/muse-spark-1.3-contributor` (agent-runbook, shared rule 4).
- E2-3: P1-T2, P1-T3. `version.rs`: `Version` (strict `MAJOR.MINOR.PATCH`), `Impact`, `bump`, `VersionLine`, `derive_line`, `mirror_divergence`. With no pending doc, `O` is `S` bumped by `fix`, so `O` is always ahead of `S`; the chapter does not say what `O` is when nothing is pending. Spec gap: R-VER-004 says `check` SHOULD warn on mirror divergence, but chapter 13 has no code for it; the text is computed and waits for an owner-assigned code (proposed `HN-V017 H-VER-MIRROR`, warn).

- E2-32: P3-T10. `graveyard.rs`: entries are TOML-frontmatter docs under a `docs/graveyard/` folder (`id` must be `grv.*`; `state` rejected, parked or revisited; `at`, `what`, `why`, `match`, `revisit-after`, `fingerprint`, optional `material` and `tripwire`). The fingerprint is the normalised identifiers (file stems, names after `pub`/`export` declarations, quoted route strings starting with `/`) and 32 min-hash values over k=5 token shingles with comment lines dropped, stored as `minhash = "b3:<8 hex digits per value>"`. One deviation from the plan's hash family: each shingle is hashed once with blake3 and the 32 values come from a splitmix of that hash with 32 seeds that are themselves blake3 keyed by the index 0..31, so a fingerprint costs one blake3 per shingle instead of 32; still deterministic on every platform. The seal fingerprints every entry that has none, from its `material` paths and the tree files its glob terms match (relative to the entry's scope directory), reading them once in the pipeline; the entry doc is rewritten with `toml_edit` (other keys and the body kept). Thresholds come from `[graveyard] ids-percent` (60) and `shingles-percent` (50).

A new or changed file (the docs-first changed set after the first seal, else `--changed`'s set; nothing otherwise) matches on a glob term (relative to the entry's scope directory) or on the stored fingerprint against the file's own fingerprint, and on an item tombstone's `paths` (prefix or glob); a change doc with `revisits` naming the entry whose `covers` takes in the file silences it. Regex terms are compared with doc text only (check never reads file text). Per-file fingerprints are computed in extraction (cached with the extras) only once the root declares a `[graveyard]` table, the opt-in that keeps the 100,000-file walk free of shingle hashing. Default severity is warn; `[rules.hn-l002]` raises it.

- E2-35: P3-T12. A revive doc is `kind = "revive"` with `revives = "<tombstoned id>"` and `as = "<id>-v<N>"` (N >= 2; the chapter gives the suffix rule but no key for the new ID). Its approval is an ordinary `[[approval]]` record: `fairlead approve <draft id>` previews `revive <old> as <new> (<draft>)` and records the fingerprint `lifecycle::revive_fp` over the draft ID, the old and the new ID (so editing either needs a new approval), with `target` = the old ID, through the unchanged terminal gate. Until then the doc is `HN-D003` (error) on its first line, as is a `revives` that names no tombstone or an `as` without a valid suffix, so the seal's check gate refuses it. Sealing it records `revive <old> as=<new> doc=<draft>` in the ledger and moves every graveyard entry the doc names in `revisits` to `state = "revisited"` with `revisited-by = "<draft>"` (R-LC-035); the tombstone is never rewritten. The new ID is declared the usual way; nothing creates it automatically.
